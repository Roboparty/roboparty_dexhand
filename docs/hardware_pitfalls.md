# DH116S 实机踩坑记录

记录日期：2026-09-29。以下汇总操作者现场反馈和本轮抓包结果，作为后续调试依据；效果描述不代表所有固件和负载下的保证。

## 1. set_move_no_home 的限制需要显式处理

操作者反馈：设置后遇到无法运动，需要通过厂家 SDK 解除相应限制。接口语义是 `0` 禁止未回零运动、`1` 允许未回零运动；如果需要允许未回零运动，应显式调用厂家 `set_move_no_home(1)`，否则应完成有效回零。

仅删除代码中的设置调用，不应假定设备已有配置随之恢复。本 SDK 已删除使能和回零路径中的 `set_move_no_home(0)`。这个开关与软件急停不同，不能用它替代撤销急停。

现在 `connect()` 在反馈配置成功后显式调用 `set_move_no_home(1)`，最多尝试 30 次（含首次），失败间隔 100 ms。只有厂家返回码为 0 且调用期间没有新增发送错误才通过；失败、取消或接收异常会导致连接失败。厂家公开 API 没有对应读取接口，因此这里确认的是 SDK 调用成功，不是设备配置读回校验，也不代表已经回零。

## 2. 整手回零效果更好

按操作者现场反馈，本轮优先使用 `home_motors(0)`，首次和重试均整手触发，不再逐轴补发。仍有轴未观察到启动时，约每秒整手重试，总计最多 30 次；整手重试可能重新触发其他轴，六轴都观察到启动后只等待完成。

## 3. 目标发送频率偏低时容易卡顿

操作者反馈低频发送效果较差，现场描述为“被电机的帧率压过去”。因此 C++、Python wave demo 均从 50 Hz 提高到 200 Hz（每 5 ms 更新一轮六轴目标），设备状态反馈仍约 50 Hz。

发送频率、反馈频率和电机内部控制频率是不同概念；目前未测量确认卡顿的具体内部原因。200 Hz 是计划发送频率，实际效果还受 SDK 调用耗时、总线负载和系统调度影响，不应只根据循环间隔认定实际达到 200 Hz。

## 4. 使能不等于解除软件急停

本轮抓包确认左手从 `0xD6`（失能、急停）变为 `0xD7`（使能、仍急停），随后回零未启动。

初始化已增加失能确认、撤销急停和反馈检查；两个 wave demo 退出改为失能、断开，不调用 `stop()`。其他程序调用 `stop()` 后，应先失能、断开，再连接重新初始化，随后重新设置参数、使能和回零。具体行为见 [README](../README.md) 的“stop 后重新初始化”。
