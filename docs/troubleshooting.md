# 已知问题与排查

先区分软件发送成功、设备反馈有效和实际运动完成。三者不是同一件事。参数、状态语义见 [API](api.md)，ROS 阶段见 [ROS 指南](ros2.md)。

## 回零后偶发不动

已观察到的现象：右手完成回零后，原运动自检连续多次目标为四指 1000，但六轴反馈位置均保持 0；之后一次完整 reset 又成功。这说明重复初始化没有稳定消除问题，不能只归因于外部 wave 没发布目标。

目前主要怀疑：原先回零后仅调用一次切位置模式 API，命令可能丢帧或未被设备处理，导致位置模式未生效，后续位置目标无法驱动手指。这是当前排查假设，尚无抓包及设备端确认能证实具体丢失或未处理的环节。

当前措施：回零完成后调用厂家切位置模式 API 30 次，间隔 20 ms，以降低单次命令漏收的概率。四指运动自检及其整轮自动 reset 重试已取消。重复发送不等于设备端模式读回，是否彻底解决故障仍需实机确认。

其他尚未排除的原因包括回零后的模式生效时序、速度/电流参数的实际生效情况及其他设备内部状态。速度与电流在回零前配置；配置 getter 检查的是厂家缓存，不能证明设备回零后仍持有相同值。厂家库还有自动恢复模式、补发参数逻辑，不能只看上层调用顺序认定漏发。

现有公开 CAN FD 手册没有给出当前实际控制模式的读回字段，0x50/0x5A 反馈的是运行状态等信息。运行状态离开“回零运行”不等于证明进入位置控制。此前检查的 x86_64 厂家库 get_control_mode 读取本地缓存，不能作为设备确认。需要厂家提供实际生效模式的 SDO/反馈定义，不能直接假定支持通用 CANopen 0x6061。

下一步有效证据是失败和成功两轮完整抓包：检查 0x01 控制/模式、0x03 速度、0x04 电流、0x02 位置，以及组合帧和实际反馈。发送计数或主机 CAN 错误计数为零，不足以证明设备执行了命令。

## 只读诊断

下面命令不会主动发运动命令。按实际接口替换 can0/can3：

```bash
ip -details -statistics link show can0
ip -details -statistics link show can3
ps -eo pid,args | grep -E 'dexhand|wave|LHandPro'
```

CAN 的 ERROR-ACTIVE 是 CAN 错误状态机中的正常可通信状态，名称本身不表示正在报错。重点检查 bus-off、error-pass、错误计数、丢包、接口是否 UP 和 FD MTU。

加载 ROS 环境后：

```bash
ros2 node list
ros2 topic info /dexhand_right/cmd --verbose
ros2 topic echo /dexhand_right/state
ros2 topic hz /dexhand_right/state
ros2 param get /dexhand_right/dexhand_node command_rate_hz
```

检查是否有多个 cmd 发布端、多个同设备驱动，以及实际加载的包路径：

```bash
ros2 pkg prefix roboparty_dexhand_ros
ls -td ~/.ros/log/*/ | head
```

ROS 日志一般位于 ~/.ros/log，SDK 的 stderr 输出可能只在启动终端或进程管理器记录中；launch.log 不一定包含所有底层日志。

## CAN 抓包

节点 ID 为 1 时，控制帧 0x501、反馈帧 0x481、SDO 请求 0x601、SDO 响应 0x581。节点不同需按 0x500/0x480/0x600/0x580 加 node_id 计算。

```bash
# 最多采集 60 秒；Ctrl+C 可提前结束
timeout 60s candump -L can3,501:7FF,481:7FF,601:7FF,581:7FF > hand-can.log
```

先开始抓包，再由操作者在清空运动空间后复现已有 reset/控制流程。保存对应 ROS 日志、参数、左右手及供电条件，避免只截故障之后的几帧。命令到时间由 timeout 退出通常返回 124，不代表抓包失败。

本机发送回环帧能说明抓包观察到主机发送，不能证明设备应用执行。状态/位置帧需结合时间序列解读，不能用一帧旧缓存判断全过程。

## 常见问题

| 现象 | 检查方向 |
| --- | --- |
| CAN interface not found / open failed | 接口名、UP、FD MTU、权限、适配器 |
| 初始化或型号检查失败 | 节点 ID、供电、波特率、手型是否 DH116S 六轴 |
| SDO 超时或反馈配置失败 | 固件支持、响应索引、其他程序竞争配置、接线 |
| feedback missing/stale | 两组反馈年龄、接收异常、总线与 CPU 调度；100 ms 失效阈值 |
| enable/disable/stop 未确认 | 新反馈是否满足状态；false 不代表物理停机 |
| home start not observed | 本次六轴回零运行是否出现；旧 homed 标志不足以通过 |
| READY 但目标不动 | 检查 cmd 实际数据、CAN 目标、参数、模式与故障；READY 无运动自检 |
| 停止发布后仍保持/执行目标 | ROS 会持续重发缓存；需要显式 stop |
| 修改代码但行为没变 | 重编对应入口，核对 ROS 包路径，退出旧进程后启动 |
| Python 导入失败 | 解释器 ABI、setup_python.sh、pip 与本地安装是否混用 |
| GLIBC/GLIBCXX not found | 系统运行库/编译器不兼容，尤其 Conda 覆盖；路径修改不能解决 ABI |
| 外部程序找不到厂家库 | 保留完整安装布局，配置应用自己的安装 RPATH |

## 已确认的使用约束

软件急停：已有抓包观察到失能且急停状态 0xD6，在使能后变为 0xD7，仍处于急停。enable 不能替代撤销急停。SDK 在 connect 中执行必要的失能和撤销流程，stop 后应完整初始化。

未回零运动限制：SDK 连接期间显式调用 set_move_no_home(1)。删除代码中的某次 setter 不意味着设备已有配置自动恢复；该设置也不是撤销急停。

回零：当前采用整手 home，未观察到全部轴启动时整手补发；这是实现策略，不保证所有固件与负载下优于其他方式。

频率：现场有较低下发频率运动不流畅的反馈，但“被电机帧率压过去”没有经过机制验证。下发频率、设备反馈频率和内部控制频率不同。当前可选 50/100/150/200 Hz，不承诺硬实时，也不代表相同反馈采样率。

SDK 与 ROS 的停止不保证保持抓握，断开不保证停机，强制 kill/断电无法执行清理。运动异常时应结合设备手册和现场条件处理，不无限自动 reset。

## 验证范围

已执行过 x86_64 C++/Python 构建、ARM64 三入口构建、CMake 安装导出和搬移检查、无硬件 API 检查、demo dry-run、ROS 未初始化启动及频率参数检查。历史也有实际连接反馈和操作者运动记录。
